## Quick-launch context menu (Results grid right-click)

Three issues found doing a real right-click pass over the menu, 2026-08-06.

- [x] **Speakeasy/Sigcheck quick-launch could hang the whole app - real thread-safety bug, fixed (2 rounds).** `results.py`'s `_start_captured_tool()` connected `worker.finished`/`worker.failed` to plain lambdas with no explicit connection type. PySide6 only auto-detects a cross-thread connection by inspecting the *receiver*'s QObject thread affinity through the bound method a signal is connected to - a lambda isn't a QObject-bound slot, so that detection can't see through it, and PySide6 silently falls back to a DirectConnection: everything the lambda calls (`_teardown_tool_thread()`'s `thread.wait()`, and `_show_tool_report()`'s `QDialog`/`QMessageBox` construction) ran on the background worker thread instead of the main thread. That's a thread calling `.wait()` on itself (self-deadlock) plus cross-thread widget parenting - exactly matches what was hit: `QThread::wait: Thread tried to wait on itself` and `QObject::setParent: Cannot set parent, new parent is in a different thread`, app then unresponsive short of Task Manager. **Round 1 fix** (explicit `type=Qt.ConnectionType.QueuedConnection` on the same lambda `.connect()` calls) did not hold - the identical crash hit again running Sigcheck (same shared method), plus new `QBasicTimer::stop` spam. A lambda still isn't a QObject Qt can resolve a receiver-thread from, connection-type override or not. **Round 2 fix**: stopped connecting to lambdas at all - `worker.finished`/`worker.failed` now connect directly to genuine bound methods of `self` (`_on_captured_tool_finished`/`_on_captured_tool_failed`), the one connection shape PySide6's auto-detection is actually documented to handle correctly. `self.sender()` identifies which worker fired (one shared slot now serves every concurrent run), and a plain `worker.title` attribute (set before `moveToThread`/`thread.start()`, so no cross-thread write) replaces what the lambda closure used to carry. This affected **both** Sigcheck and Speakeasy (same shared code path). Winnow-only - Rowan's WinForms events don't have this footgun. No automated test (GUI/Qt code isn't unit-tested in this project - no display in the dev sandbox). **Confirmed working end-to-end (2026-08-06)** - a real test pass ran Sigcheck (clean report), Ghidra headless (legible confirmation), and Speakeasy (legible warning dialog, emulation completed, results reported) all in one pass with no hangs, no crashes, no terminal spam. Round 2 held.

The complaint ("no other windows open, no messages... appears nothing happens") is valid either way. Headless analysis still runs unattended after that with no progress indicator by design (unchanged) - this is just a "yes, it started" acknowledgment.

- [x] **`QMessageBox` text illegible (near-black on near-black) - separate bug from the Speakeasy thread issue, fixed.** Screenshots of the Ghidra success dialog (the new one just added above) and the Speakeasy confirmation dialog both showed body text almost unreadable against the background. Confirmed this is unrelated to the threading fix above: the Ghidra dialog is a plain synchronous `QMessageBox.information()` call with zero threading involved, yet shows the identical symptom. Root cause: `binsifter/gui/__main__.py` never applies any app-wide `QApplication.setStyleSheet()`/`setPalette()` (confirmed via grep - genuinely nothing exists) - every other widget in the app gets its colors from its own explicit per-widget stylesheet, but `QMessageBox.information/warning/critical()` calls (used everywhere - `main_window.py`, `results.py`, `settings.py`) get zero BinSifter theming and fall through entirely to Qt's own rendering. On a Windows 11 machine with OS-level dark mode on, Qt6 auto-detects that and applies a dark palette to native dialogs, but the auto-derivation has a well-known gap where the background darkens correctly while text-color roles don't lighten to match - not a BinSifter bug in the usual sense, but a real, user-visible defect either way. Winnow-only; Rowan's WinForms `MessageBox.Show()` uses a completely different native rendering path with no equivalent bug reported on Rowan. **Confirmed fixed (2026-08-06)** - screenshots of the Ghidra and Speakeasy dialogs both show fully legible text now.

## Archive/compressed-file support

- [x] **Archive/compressed-file support (zip/tar/gzip/7z) - requested 2026-08-06, implemented 2026-08-07 in both Winnow and Rowan.** New `core/archive.py` module + wiring into `engine.py`'s `scan_directory()` (Winnow); a direct port of the same design into the PS1's `Start-ScanEngine` dispatcher (Rowan, see below for the one real implementation difference). Three open design questions from the original ask were put directly via AskUserQuestion rather than guessed at; all three are now built exactly as confirmed, in both variants:
  1. **Format scope: zip, tar (+ compressed-tar variants), standalone gzip, and 7z.** RAR was explicitly NOT included - the confirmed choice was the zip/tar/gzip/7z option, not the "also add RAR" one; RAR would need an external `unrar`/`unar` binary the same way Sigcheck/Ghidra need a configured `.exe`, deferred until there's a real need. Winnow: Python stdlib `zipfile`/`tarfile`/`gzip` for the first 3 (no new dependency), `py7zr` (new dependency) for 7z. Rowan: all 4 formats go through one tool, 7-Zip's own CLI (`7z.exe`, new `SevenZipExe` entry in `$ToolFileNames` - discovered under ToolsDir the same as every other tool), rather than a separate library per format - matches Rowan's existing "shell out to a real tool" convention (yara64.exe/capa.exe/ssdeep.exe/etc.) instead of translating Winnow's specific implementation choice.
  2. **Password-protected archives: a pre-scan pass finds every locked archive under SrcDir before the real per-file scan starts, prompts for all of them at once in a single batch dialog, then extracts with whatever passwords were supplied** - not a per-file mid-scan interruption. Archives nobody has a working password for get copied (never moved - the analyst's original evidence under SrcDir is never touched) into `<ReportDirectory>/password_protected/` for external cracking tools (John/hashcat/etc.). Winnow: `gui/archive_password_dialog.py`'s `ArchivePasswordDialog`. Rowan: a WinForms port of the same dialog, `Show-ArchivePasswordDialog`, next to `Show-ToolReportWindow`.
  3. **Extracted files show up in Results as their own ordinary rows, not grouped/nested under the archive's row** - `FileRecord.SourceArchive` (new field in both variants' `FileRecord`, also a new CSV column and Results grid column, "Source Archive") is blank for a directly-scanned file and holds the immediate containing archive's path for an extracted one (the immediate parent, not necessarily the top-level archive, if archives are nested a few levels deep).

  **The architecture question flagged as the hardest part turned out to have a much simpler answer than it looked, in both variants.** The original concern was "how does a background worker pop a dialog on the GUI thread and block for a password" - genuinely looked unsolved when this was scoped. Working through it: archive expansion doesn't need to happen inside the per-file worker pool at all, in either variant. It runs as a **serial pre-scan step**, in the exact same place NSRL/blocklist/YARA/capa already get loaded once, before the pool/runspace-pool is created. **Winnow**: that pre-scan step already runs on a background **QThread** (`main_window.py`'s `_ScanWorker`), in the *same process* as the GUI, not a separate `multiprocessing.Pool` process - a QThread can signal the GUI thread and block on a `threading.Event` for an answer using ordinary, safe Qt cross-thread coordination. **Rowan**: the dispatcher runs in its own PowerShell *runspace* (a thread, not a process, sharing the same in-process memory as the GUI runspace) - rather than a direct cross-runspace `Control.Invoke()` (untested and genuinely risky to get right blind, with no Windows/WinForms environment available to verify it in), this reuses the SAME polled-shared-state pattern the dispatcher already relies on for pause/stop/progress: `$ScanControl` (a `[hashtable]::Synchronized(...)`) grows 3 new fields (`PendingPasswordRequest`/`PasswordMap`/`PasswordMapReady`), the dispatcher sets the request and polls-and-blocks on `PasswordMapReady`, and `$refreshTimer.Add_Tick` (the same 750ms UI-thread timer that already drains logs/dirty-record queues) notices the pending request, shows `Show-ArchivePasswordDialog`, and writes the answer back. Same "block a background worker, let the UI thread answer" shape as Winnow, built out of each variant's own already-proven cross-thread/cross-runspace primitives rather than either forcing one variant's mechanism onto the other or inventing a third, unverified one. By the time either variant's worker pool actually starts, every extracted file is just an ordinary file on disk with a real path - the pool/runspace-pool workers themselves needed **zero changes** in either variant.

  Two sub-questions that weren't put directly to a decision (format scope / password-prompt architecture / Results display were judged the three load-bearing ones) got documented defaults instead of blocking on an answer, same in both variants:
  - **Nested archives** (a zip inside a zip) are expanded recursively, bounded by a max nesting depth of 3 (`core/archive.py`'s `MAX_NESTED_DEPTH` / the PS1's `$MaxNestedArchiveDepth`) - a zip inside a zip inside a zip inside a zip is left as a plain extracted file past that point, not further opened. Easy to change later, not worth blocking on.
  - **Extracted files live under `<ReportDirectory>/extracted_archives/<archive-stem>_<short-hash>/`**, kept after the scan (not a temp dir cleaned up afterward) - same "persisted next to Reports" convention `ghidra_projects`/`generated_rules` already use, and needed anyway so Ghidra/Sigcheck/Speakeasy quick-launch (which need a real, still-existing file path) can be pointed at anything extracted from an archive.

  **Winnow**: covered by `tests/test_archive.py` (31 tests: format classification, password detection for zip/7z, extraction, wrong-password handling, nested recursion including the depth-cap boundary, name-collision handling in the unresolved-archives directory) plus a new end-to-end regression test in `tests/test_engine.py` (`test_archive_contents_scanned_through_real_worker_pool_with_source_archive_set`) that runs a real archive through the real `multiprocessing.Pool` rather than just `archive.py` in isolation - this caught a real bug during manual verification (see below) that an `archive.py`-only unit test never could have. Full test suite: 161 passed, same 3 pre-existing/environment-specific failures as before this work (confirmed unrelated by re-running them against the unmodified `engine.py` from HEAD - identical failures either way): a capa-rules-corpus gap in the dev sandbox, a `multiprocessing`-spawn/`monkeypatch` interaction that predates this change, and a missing sandbox fixture file.

  **Real bug caught and fixed during Winnow's end-to-end verification (2026-08-07, before this ever shipped):** `SourceArchive` was originally set on the placeholder `FileRecord` dict built *before* the pool ran, then silently clobbered the instant each file's real result came back from a worker (`records[result.record.Path] = result.record` replaces the whole object, since each pool worker builds its own fresh `FileRecord` with no knowledge of `source_archive_by_path`) - a real scan against a zip showed every extracted file's `SourceArchive` coming back blank despite the assignment code existing elsewhere in the function. Fixed by applying `source_archive_by_path` *after* the pool's completion-draining loop instead of before it starts; confirmed via a manual end-to-end run and the new regression test above, both passing. **This bug could NOT have happened in Rowan** - PowerShell runspaces share one process's memory, so every worker mutates the SAME shared `FileRecord` object in place (`$FileRecords[$FilePath].SomeField = ...`) rather than a spawned Python worker PROCESS building and returning a separate copy that has to be merged back in; Rowan sets `.SourceArchive` once, at record-creation time, with no equivalent clobbering risk to guard against.

  **Rowan verification caveat, stated plainly:** this dev sandbox is Linux-only with no interactive Windows/WinForms environment, so - unlike Winnow, which was exercised with real end-to-end scans - the Rowan port could only be verified by careful manual read-through plus mechanical checks (brace/paren/bracket balance before and after each edit, confirming every new function is defined exactly once, cross-checking `Invoke-ExternalTool`/`$ScanControl`/`$refreshTimer` call signatures by hand against their real definitions elsewhere in the file). `7z.exe`'s exact CLI behavior (the `-slt`/`Encrypted = +` password-detection heuristic in particular) was corroborated against 7-Zip's own documented behavior, not tested against a real `7z.exe` binary. **A real scan against a small test folder with a plain zip and a password-protected one should be run before trusting this in a real case** - flagging this explicitly rather than presenting it with the same confidence as the Winnow half, which WAS run for real.

## Rowan startup: $BinSifterRoot defaulting to C:\Windows\System32

- [x] **Fixed 2026-08-08.** Hit while testing the archive feature: launched Rowan and got two stacked warning dialogs - "couldn't determine its own script folder... will be created under the current folder instead: `C:\Windows\System32`", immediately followed by "default folder isn't writable... will be created here instead: `C:\Users\Jay\AppData\Local\BinSifter`". The second dialog's fallback (a per-user, guaranteed-writable folder) already made this harmless in practice, but it was correctly flagged that System32 should never have been the *candidate* default in the first place - "The default should be the GitHub directory or whichever directory Rowan is launched from."
  - **Root cause:** `$PSScriptRoot`/`$PSCommandPath`/`$MyInvocation.MyCommand.Path` all came back empty for this launch (same class of gap the code already called out - certain VS Code "Run and Debug" configs, or any invocation that doesn't leave a real, plain `.ps1`-file-backed script context, don't populate these the normal way). The old fallback for that case was `(Get-Location).Path` - PowerShell's own session *current directory*, which is a completely different thing from "where the script file lives" or "where Rowan was launched from," and for several real launch paths (a shortcut with no "Start in" set, some debug configs) that current directory defaults to `C:\Windows\System32` since that's where `powershell.exe` itself lives - not because BinSifter's own folder is anywhere near there.
  - **Fix:** added a fourth resolution tier, tried *before* giving up and guessing: parse this process's own command line (`Get-CimInstance Win32_Process -Filter "ProcessId=$PID"`) for a real `.ps1` path. This works regardless of which automatic variable failed, since the actual script path is always present as a literal command-line argument no matter how PowerShell was invoked (double-click, right-click "Run with PowerShell", a shortcut, VS Code Run/Debug, `pwsh -File`, `-Command "& '...'"`) - genuinely finds "whichever directory Rowan is launched from" as originally requested, rather than guessing. Only if that also comes up empty (e.g. the script's text was piped/typed into a session with no real file backing it at all) does it fall through to a last resort - and that last resort is now `%LOCALAPPDATA%\BinSifter` directly, not `Get-Location`, so System32 (or any other surprising session-CWD artifact) can never again show up as a candidate root, not even transiently in a dialog. The existing writability belt-and-suspenders check (added 2026-08-03 for this exact System32 case, previously the only defense) stays in place unchanged as a second layer, for the separate scenario of a *correctly*-resolved script folder that happens to live somewhere the current user can't write to (a read-only mount, a locked-down machine, etc.).
  - **Verification caveat, same as the rest of Rowan's port this cycle:** no interactive Windows/WinForms environment in this dev sandbox to actually run this and confirm the CIM-based lookup resolves correctly end-to-end - verified via careful manual read-through and the mechanical brace/bracket/paren balance check (balanced: 1185/1185 braces, 1047/1047 brackets, parens at the same pre-existing -1 baseline as before this edit). Worth relaunching however this was originally triggered (sounds like it wasn't a plain double-click or `pwsh -File`, since those already worked correctly before this fix) to confirm it now resolves to the real BinSifter/GitHub folder instead of prompting at all.

## Catalog-based (.cat) signature verification

- [x] **Implemented in Winnow 2026-08-08 - Rowan needed zero code changes.** Added directly after the "38 unparseable files" investigation surfaced the separate, longer-standing gap noted in `authenticode.py`: a large fraction of Windows' own inbox binaries (notepad.exe, calc.exe, etc.) aren't embedded-signed at all - they're validated against a system catalog file (`.cat`, under `C:\Windows\System32\CatRoot\`) instead, and `check_signature()` was previously only checking each file's own embedded PE certificate table.
  - **Rowan: confirmed to need no changes at all.** Rowan calls the native `Get-AuthenticodeSignature` cmdlet, which goes through Windows' own `WinVerifyTrust` under the hood - and `WinVerifyTrust` already checks catalog files transparently as part of normal signature verification on any real Windows machine with an intact `CatRoot`. This gap only ever existed in Winnow, which does its own PKCS#7/trust-chain verification via `signify` instead of deferring to the OS. Per the "implement across all variants" convention (see Conventions section at top), this is the one legitimate exception: there's nothing to port because Rowan was never missing the behavior in the first place.
  - **Winnow implementation:**
    - `core/config.py`: new `CatalogDirectory` Settings-page field (default `""`), added to `_CACHE_FIELDS`. Optional, same as `GhidraDir` - blank means "skip catalog checks," not an error.
    - `core/authenticode.py`: new `parse_catalogs(catalog_directory)` - enumerates every `*.cat` file directly under the directory and parses each into a `CertificateTrustList` via `CertificateTrustList.from_envelope()`; a single malformed `.cat` is logged and skipped, not fatal to the batch. `check_signature()` gained an optional `catalogs` parameter - each provided catalog is offered to the file via `AuthenticodeFile.add_catalog(catalog, check=True)` before `explain_verify()` runs; `check=True` means signify itself only actually attaches a catalog if the file's hash is found inside it (`find_subject()`), so passing every configured catalog to every file is safe and cheap. `iter_signatures()`'s existing default `signature_types="all"` already combines embedded + catalog signatures, so no other verification-path changes were needed.
    - `core/engine.py`: catalogs are parsed **once per worker process**, not once per file - `_pool_worker_init()` calls `authenticode.parse_catalogs(config.CatalogDirectory)` at worker startup and stores the result in a new `_worker_catalogs` global, mirroring the existing YARA-rules-compiled-once-per-worker pattern (a parsed `CertificateTrustList` wraps `cryptography` objects that aren't cleanly picklable across the `multiprocessing.Pool` process boundary, the same reason YARA's compiled `Rules` object is re-compiled per worker rather than handed down from the parent). The per-file worker call is now `authenticode.check_signature(path, catalogs=_worker_catalogs)`.
    - `gui/pages/settings.py` / `gui/settings_validation.py`: new "Catalog (.cat) directory - optional" Settings field, folder picker, validated the same way as `GhidraDir` (blank is valid; if given, must be a real existing directory) - factored into a shared `_OPTIONAL_DIR_FIELDS` loop rather than a second hand-copied `GhidraDir`-shaped `if`/`elif` block.
  - **Tests:** `tests/test_authenticode.py` gained coverage for `parse_catalogs()` (blank/missing/empty/non-`.cat`/malformed-`.cat`/file-instead-of-directory inputs, all degrading gracefully to an empty list rather than raising) and `check_signature()`'s new `catalogs` wiring (every provided catalog gets offered to `add_catalog()`; one catalog raising doesn't sink the others or the overall check; omitting the parameter entirely is unchanged from pre-2026-08-08 behavior) using a lightweight fake `AuthenticodeFile` stand-in rather than real crypto. Full suite: 173 tests, 170 passed - same 3 pre-existing/unrelated failures as before this work (confirmed via `git show HEAD:...` comparison: 2 in `test_engine.py` around capa-rules-corpus/progress-status gaps in the dev sandbox, 1 in `test_capa_scan.py` - none touch authenticode/catalog code, none introduced by this change).

That could not be completed from this dev sandbox: there's no Windows machine here to pull one from directly, and the most likely alternative source - `signify`'s own library test fixtures (`oem89.cat`, `catfiletest.cat`, etc., referenced in its `tests/authenticode/file_types/test_ctl.py`) - turned out to be excluded from the PyPI sdist entirely (`tests/test_data/` isn't packaged), and fetching them from GitHub directly was blocked at every turn: `raw.githubusercontent.com`, `api.github.com`, and `codeload.github.com` all return `403 blocked-by-allowlist` from this sandbox's network policy (only the plain `github.com` web UI is reachable, which redirects tarball downloads straight into the blocked `codeload.github.com`). **What's ready to go:** a `Catalogs/` folder now exists at the repo root, gitignored (see `.gitignore` and `Catalogs/README.txt`) exactly as asked - drop a real `.cat` there (e.g. copied from a real machine's `C:\Windows\System32\CatRoot\{GUID}\`, which counts as "known good" since that Windows install already trusts it) and point Settings' new "Catalog Directory" field at it to exercise this for real.
