Not a BinSifter bug, just a real-world setup note worth remembering for future test rounds: point `SrcDir`/`ToolsDir`/`NsrlPath` at local disk, not a shared/mounted folder, for anything beyond a tiny smoke test.
- [x] **REAL BUG FOUND AND FIXED: archive-expansion scan dispatch crashed immediately with "Cannot find an overload for "new" and the argument count: "1"." (`BinSifter-Rowan_v1.3.0-beta.1.ps1`, scan-engine dispatcher).** Second scan (19 files - 7 archived Malware Bazaar samples, all password-protected, extracted successfully via the shared-password prompt) got all the way through enumeration and archive extraction (`Archive expansion pass 2: 12 more file(s) extracted...`, `Target queue populated: 19 files.`) and then died on the very next line, before a single file was dispatched to a worker - Scan Queue showed all 19 files stuck at `Queued`/0% forever ("Scan finished. 0 / 19 files completed."). Root-caused from the real log (`Rowan_logs.txt`): `$orderedPaths` starts out as a genuinely .NET-typed `List[string]` (`EnumerationResult.Files`), but the archive-expansion code above rebuilds it via `$orderedPaths = @($orderedPaths) + @($expansion.ExtractedFiles)` (and again for password-resolved files) - PowerShell's `@()` array-subexpression operator flattens that into a loosely-typed `System.Object[]`, even though every element is still genuinely a string. The next line, `[System.Collections.Generic.Queue[string]]::new($orderedPaths)`, has to resolve between `Queue`'s `(int capacity)` and `(IEnumerable[string] collection)` constructors, and PowerShell's `::new()` overload binder can fail to disambiguate those two against an untyped `Object[]` argument - "Cannot find an overload for 'new'" is PowerShell's own wording for exactly that binder failure, thrown before the constructor itself ever runs. This is the **only** 1-argument `::new()` call on a generic .NET collection anywhere in the file (confirmed via search - every other generic-collection construction elsewhere uses either zero arguments or an `int` capacity), and archive expansion had never previously run end-to-end against a live Rowan scan reaching this exact line - so this had been sitting latent since archive support shipped, never triggered by any prior confirmed real-Winnow-only or synthetic Rowan test. **Fixed** by casting explicitly to `[string[]]` right at the point of construction (`[System.Collections.Generic.Queue[string]]::new([string[]]$orderedPaths)`) - a genuine `String[]` unambiguously satisfies `IEnumerable[string]`, no binder guesswork left. Bracket/brace/paren balance re-verified on just the diff's added/removed lines (both fully balanced, 0 errors) via the same quote/comment-aware scanner used for every other Rowan-only change this project can't run `pwsh` to check directly. **Not yet re-tested against a real scan** - needs a third FLARE VM run to confirm the fix actually resolves it, since this dev sandbox still has no `pwsh` to verify directly.
- [x] **RESOLVED: "Capa: version unavailable" was a probe-timeout issue, not a broken capa.** Asked for `capa.exe --version` run directly in a terminal on the same FLARE VM - answered immediately and correctly (`capa.exe 9.3.1`), confirming capa.exe itself is fine; the disconnect was specifically between how `Get-VersionText` invokes it and a plain terminal run. capa's official Windows release is a PyInstaller onefile executable, which self-extracts its whole bundled Python runtime into a fresh `%TEMP%` folder on every launch (not cached between runs) - real, documented PyInstaller behavior, not a guess - making it a fundamentally heavier launch than `yara64.exe`/`ssdeep.exe` (small native binaries, near-instant startup). `Get-VersionText` used one flat 3-second timeout shared across all three tools, which wasn't well-suited to capa's launch profile, especially on a slower-disk analysis VM. **Fixed** by bumping the timeout to 10 seconds - this probe only ever runs once at startup or right after a Settings save, never a hot path, so a longer worst-case wait costs nothing real, and it still fails gracefully to `'version unavailable'` if a tool is genuinely hung. **Not yet re-confirmed against a real BinSifter run** - needs the next FLARE VM test to verify the status bar now shows a real capa version instead of "version unavailable."

## First real Winnow installer test - 2026-08-09

Same day as the Rowan FLARE VM test above, but this one was on both a host system and FLARE VM, and it's Winnow-specific throughout - Rowan shells out to a separate `speakeasy.exe`-equivalent process for its own emulation quick-launch, so it never had this exposure.

- [x] **REAL BUG FOUND AND FIXED: the whole app crashed at startup, on BOTH machines, with an ImportError chain ending in unicorn's "ERROR: fail to load the dynamic library."** Traceback ran `__main__.py` -> `main_window.py` -> `results.py` -> `core/speakeasy_scan.py` -> `speakeasy/__init__.py` -> ... -> `speakeasy/engines/unicorn_eng.py` -> `import unicorn` -> unicorn's own native-DLL loader. Root cause: `results.py` does `from binsifter.core import ai_export, speakeasy_scan` at its own module level (so the GUI can build the Speakeasy quick-launch menu item), and `speakeasy_scan.py` used to do a plain top-level `import speakeasy` - `speakeasy`'s own `__init__.py` eagerly imports its ENTIRE Windows-emulation stack down to `unicorn` at import time, which loads `unicorn`'s native DLL via `ctypes` immediately, not lazily. That means ANY failure to load that one native DLL took down the entire application before the main window ever appeared, for every user - even someone who never intends to touch Speakeasy emulation at all. Leading explanation for why the DLL itself failed to load: `speakeasy-emulator` hard-pins `unicorn==1.0.2` (see `pyproject.toml`'s dependency comment), an old release whose prebuilt Windows wheel is known in the wider community to need the Microsoft Visual C++ Redistributable (x64) present on the target machine - plausible on both a fresh-ish host and a FLARE VM, though which exact machine was missing what couldn't be confirmed from this Linux dev sandbox. **Fixed with two layers, since the exact root cause couldn't be nailed down for certain without a real Windows repro:**
  1. **`binsifter/core/speakeasy_scan.py`: made the import itself resilient**, same graceful-degradation philosophy `emulate_file()` already used for a target file speakeasy can't handle. The module-level `import speakeasy` is now wrapped in try/except; a failure is stored (`_IMPORT_ERROR`) instead of propagating, and `_DEFAULT_CONFIG_PATH` degrades to `""` rather than crashing on `speakeasy.__file__`. `emulate_file()` checks that stored failure first and returns a normal `SpeakeasyResult` with an actionable `.error` message (names the Visual C++ Redistributable as the likely fix) instead of ever letting the original exception reach `results.py`'s import and crash the app. Every other BinSifter feature (YARA, capa, ssdeep, hashing, Authenticode, the rest of the Results grid) has zero dependency on unicorn/speakeasy and is unaffected either way - only the Speakeasy emulation action itself degrades, with a clear message, instead of the whole app dying. Covered by 3 new tests in `tests/test_speakeasy_scan.py` (this Linux sandbox's real speakeasy/unicorn install works fine - no Windows DLL to fail here - so the real failure mode is simulated by monkeypatching the module's post-failure state directly, not by forcing a real ImportError through a working library).
  2. **`installer/winnow.spec`: added explicit `collect_all("unicorn")`**, wired into `Analysis()`'s `binaries`/`datas`/`hiddenimports` alongside the existing `mscerts`/`speakeasy` collections. Nothing previously explicitly collected unicorn's own native binaries - PyInstaller's automatic community hook (via `pyinstaller-hooks-contrib`, a transitive dependency of `pyinstaller` itself) should normally catch this, but there was no way to confirm that from this Linux sandbox against a real Windows build, and this costs nothing if the automatic path already had it covered.
  3. **README's Requirements section now names the Visual C++ Redistributable (x64) as a Winnow prerequisite** on Windows, with a link and a note that only Speakeasy emulation is affected if it's missing.
  Full test suite re-run: 205 passed (adding 3 new tests to the existing `tests/test_speakeasy_scan.py` - a first attempt at this accidentally overwrote that file's 10 pre-existing tests instead of extending it, caught before committing and merged back in, all 13 tests in that file now pass together), same 3 pre-existing unrelated failures as every prior run this session. **Not yet re-tested against a real installer build** - needs both machines re-tested against a freshly-built installer to confirm the app now starts cleanly either way (with or without the Redistributable installed).
- [x] **Asked directly: is Microsoft Defender's "Trojan:Win32/Malgent" flag on `BinSifter-Winnow.exe` related to Speakeasy?** Very likely yes, though this can't be fixed from BinSifter's own code the way the crash above could. `Trojan:Win32/Malgent` is Defender's generic ML/heuristic bucket for "structurally or behaviorally suspicious, not a specifically identified family" - not a manually-confirmed detection. Bundling `unicorn` (a full CPU emulator, capable of executing arbitrary code in an emulated environment) and `speakeasy` (a Windows API emulation framework literally built for running malware-like code paths) inside a PyInstaller-built executable is a well-known, common heuristic trigger for exactly this class of generic AV flag - other real malware-analysis tools built the same way (Python + PyInstaller + an embedded emulator/hooking library) hit this regularly, it isn't unique to BinSifter. `winnow.spec` already disables UPX compression specifically to avoid stacking a second well-known false-positive trigger on top (see that spec's own comment) - this is the same category of problem, just not something a packaging flag can turn off, since the emulation capability itself is what's being flagged, not just the packer shape. **Not something to chase further in code** - the standard real-world path for this is submitting the built executable to Microsoft's own file-submission portal (submit.microsoft.com) for a false-positive review once a build is otherwise stable, which is a normal, expected step for legitimate tools in this category, not a BinSifter-specific workaround. Once the startup-crash fix above lands, BinSifter's own existing Defender-exclusion Settings button (see the Quick-launch/Defender sections elsewhere in this file) is also available as a local workaround for an individual analyst's own machine, worth pointing out since it couldn't even be reached before this fix (the app crashed before Settings was ever reachable).

## Second real Rowan installer test (real case work) - 2026-08-10

Installer itself confirmed still working cleanly (only manual step needed was copying `7z.exe` into the tools directory, same as the documented archive-support prerequisite). A real 652-file case scan ran to completion; three issues surfaced from the logs and a right-click pass over Results afterward.

- [x] **REAL BUG FOUND AND FIXED: draft YARA rule generation silently skipped every run - `Measure-Object -Property @{Expression=...}` isn't valid syntax for that cmdlet.** Log showed: `Draft YARA rule generation skipped due to error: Cannot bind parameter 'Property'. Cannot convert the "System.Collections.Hashtable" value of type "System.Collections.Hashtable" to type "Microsoft.PowerShell.Commands.PSPropertyExpression".` Root cause confirmed against PowerShell's own documented behavior (not guessed): `Select-Object`/`Sort-Object`/`Group-Object`/`Format-Table` all accept the `@{Name=...; Expression={...}}` calculated-property hashtable idiom, but `Measure-Object`'s `-Property` parameter is typed `PSPropertyExpression[]`, not `[object[]]`, and does **not** accept that hashtable form at all - only a bare scriptblock. The size-range computation for each SSDEEP-cluster draft rule (`$minSize`/`$maxSize`, used to build the `filesize >= X and filesize <= Y` condition) used the hashtable form, so every single cluster's rule generation threw, was caught by the surrounding `try`/`catch`, and logged as skipped - this had never worked, on any run, since the feature shipped (the same reason the 132 real `generated_rules/*.yar` files already in `Reports/` all fall back to the "no common strings found" skeleton condition with no filesize bound: the per-cluster size range was never successfully computed even when common strings *were* found). **Fixed** in `BinSifter-Rowan_v1.3.0-beta.1.ps1`: replaced the two separate hashtable-based `Measure-Object` calls with one bare-scriptblock call requesting both `-Minimum` and `-Maximum` at once (`Measure-Object -Property { (Get-Item -LiteralPath $_.Path -ErrorAction SilentlyContinue).Length } -Minimum -Maximum`) - also cheaper than before (one `Get-Item` pass per member instead of two). Bracket/brace/paren balance re-verified via the same quote/comment-aware scanner used for every other Rowan-only change this dev sandbox can't run `pwsh` to check directly (net delta across added/removed lines: 0 for every bracket type). **Not yet re-run against a real scan** - needs a real case run to confirm rules now generate with a real filesize condition instead of skipping.
- [x] **REAL BUG FOUND AND FIXED: "Export for AI analysis" crashed on every single use - `Exception calling "Contains" with "1" argument(s): "Value cannot be null. (Parameter 'key')"`.** Traced to `ConvertTo-AiExportMarkdown`'s hash-summary line: `foreach ($pair in @(, @('MD5', 'MD5'), @('SHA1', 'SHA1'), @('ssdeep', 'SSDEEP')))`. This file uses a real, working idiom elsewhere for building an array of 2-element row-arrays across *multiple lines* (e.g. `-Rows @( , @('Status', ...) , @('Signer', ...) )`, one `,`-prefixed row per line) - each row there is its own newline-separated statement, and the leading `,` is needed to stop `@()`'s pipeline-style statement-output collection from auto-unrolling that row's 2 elements into 2 separate items. The hash-summary line copied that same leading-comma habit onto a **single-line, already comma-joined list** instead - a fundamentally different construct, since there's no per-statement pipeline unroll there for the comma to cancel out. The result: only the *first* item (`@('MD5', 'MD5')`) got an extra, uncancelled array wrapper (`@(@('MD5','MD5'))`), while the other two items were unaffected - so on the loop's first iteration, `$pair` was a 1-element array, `$pair[1]` silently returned `$null` (PowerShell doesn't throw on a simple out-of-range array read), and `$data.Contains($null)` (an `OrderedDictionary`) threw exactly the observed exception. Deterministic, not data-dependent - this fires on every call, on the very first loop iteration, regardless of which file is selected, matching the real report exactly. **Fixed** by dropping the stray leading comma (`@(@('MD5', 'MD5'), @('SHA1', 'SHA1'), @('ssdeep', 'SSDEEP'))`) - correct for a single-line comma-joined list, where `@()` just needs to wrap the list, not protect each element from a pipeline unroll that doesn't happen here. Confirmed via a targeted search (`@(,\s*@\(` pattern) that this specific single-line-with-leading-comma antipattern appears exactly once in the file - the multi-line `-Rows @( , @(...) ... )` calls elsewhere (Signature/YARA/capa/ssdeep-imphash/Other sections) use the correct per-line idiom and are unaffected, confirmed by the same reasoning that explains why they've never thrown. Bracket/brace/paren balance re-verified the same way as the item above (net delta: 0). **Not yet re-run against a real scan** - needs confirmation the export now completes and produces a correct Markdown hash-summary line.
- [x] **INVESTIGATED: Speakeasy grayed out in the Results right-click menu - not a bug, a documentation gap.** Same "check before guessing" discipline as the earlier Sigcheck investigation: `speakeasyItem.Enabled` is only true once `$Config.SpeakeasyExe` resolves to a real file named `speakeasy.exe` under the configured tools directory - working exactly as designed, and grayed out is the correct, honest state when that file isn't there. The real gap is that, unlike Sigcheck/Ghidra/yara64/capa/ssdeep/7z (each a standalone binary you can just download and drop into the tools folder), **Speakeasy has no such standalone release** - it's the Mandiant/Google `speakeasy-emulator` Python package (`pip install speakeasy-emulator`), and the `speakeasy.exe` this feature needs is the console-script launcher stub pip generates inside that Python environment's `Scripts\` folder, not something to search Sysinternals-style download pages for. The Settings/Help text and the click-time "not configured" message both described it exactly like every other portable-binary tool, which would send anyone looking for a direct download on a dead end. **Fixed the guidance, not the logic** (the enable/disable check itself is correct and needs no code change): both the Help page's "speakeasy.exe" bullet and the click-handler's not-found message now spell out the actual path - install `speakeasy-emulator` via pip, then copy `speakeasy.exe` out of that environment's `Scripts` folder into the tools directory, same as any other tool once it's there. **Not yet confirmed end-to-end** - worth a real pass once `speakeasy.exe` is copied in per the new guidance, to confirm the menu item enables and a real emulation run succeeds (the underlying `Invoke-CapturedTool`/JSON-summary path itself wasn't touched this pass, so it's presumed still correct from its original implementation, not re-verified here).

## Re-test after first-round fixes (same day, 2026-08-10)

Fixed `.ps1` was dropped straight into the installed copy (no reinstall needed - see the installer-doesn't-compile-anything note elsewhere) and re-run against the same real case. Both remaining issues below are a direct consequence of the two try/catch-wrapped code paths above having *never executed past their first bug* in any prior test - fixing bug #1 in each let execution reach a second bug that had been sitting there the whole time, unreachable and untested, same shape as the archive-dispatch/capa-timeout pattern from the FLARE VM round.

- [x] **REAL BUG #2 FOUND AND FIXED: draft YARA rule generation now failed differently - `The term 'if' is not recognized as a name of a cmdlet, function, script file, or executable program.`** Once the `Measure-Object` fix let `$minSize`/`$maxSize` compute successfully, execution reached the cluster's condition-string-building lines for the first time ever: `$cond = "uint16(0) == 0x5A4D and " + (if ($sizeCondition) { "$sizeCondition and " } else { '' }) + "(3 of them)"` (and the equivalent `$fallbackCond` line just below it). Confirmed against documented PowerShell grammar (not guessed): bare `(...)` parens are the "parenthetical expression" operator and only accept a single **pipeline**, not a **statement** - `if`/`else` is a statement, not an expression, so wrapping it in bare `(...)` and using the result as an operand of `+` made the parser try to invoke `if` itself as an external command name. `$(...)` (the full subexpression operator) is the construct that actually supports statements like `if`/`for`/`while` inline - `(...)` does not, despite `$x = if (...) {...} else {...}` working fine as a plain top-level assignment (that's a different code path - PowerShell captures a whole statement's output on direct assignment, which isn't the same as embedding it as a sub-expression inside a larger expression). **Fixed** by precomputing the conditional piece into its own variable via a normal top-level `if`/`else` assignment first (`$sizePart = if (...) {...} else {...}`), then concatenating that plain variable - sidesteps the bare-parens restriction entirely rather than switching to `$(...)`. Searched the rest of the file for the same `+ (if (...) {...} else {...})` antipattern (used as an operand inside a larger expression, not a `$(if...)`-wrapped inline value or a plain top-level assignment) - every other `(if (...) {...} else {...})` in the file is correctly `$(if ...)`-prefixed (11 occurrences, e.g. the Scan Queue grid's Yes/No cell values, `Add-Log $(if ...)`), so this was the only instance of the bug. Bracket balance re-verified the same way as every other change this pass (net delta: 0 across the whole diff). **Not yet re-run against a real scan.**
- [x] **REAL BUG (self-inflicted) FOUND AND FIXED: "Export for AI analysis" now failed with `You cannot call a method on a null-valued expression.`** This one was introduced by the *first* round's own fix, not a pre-existing bug: removing the leading comma from the hash-summary `foreach` loop was done as a targeted string replacement that (by mistake) also dropped the line right above it, `$hashBits = [System.Collections.Generic.List[string]]::new()` - so `$hashBits` was left referencing nothing, and `$hashBits.Add(...)` on the loop's first successful match called `.Add()` on `$null`. Static read-through of every other line in `Get-AiExportCompactFields`/`ConvertTo-AiExportMarkdown`/`ConvertTo-AiExportJson`/`Export-FileForAiAnalysis` (checked against every `BinSifter.FileRecord` field that can legitimately be `$null` for a real file) turned up nothing else unguarded before this was found - genuinely just a dropped line from the prior edit, confirmed by diffing against what the function looked like before that edit. **Fixed** by restoring the `$hashBits` initialization line. Also added stage-labeled `try`/`catch` around `Export-FileForAiAnalysis`'s five steps (prepping the output dir, computing the filename, building the Markdown, writing the Markdown, building the JSON, writing the JSON) so that if there's a *third*, still-undiscovered bug in here, the next failure names the exact stage instead of a bare top-level message - this dev sandbox still has no `pwsh` to step through it directly, so this is a deliberate concession to that limitation rather than a claim the function is now fully verified. **Not yet re-run against a real scan.**

## Second real Rowan installer test, cross-machine (host + FLARE VM) - 2026-08-13

Host machine: installed, ran a real scan against actual casework, completed with no issues. Same installer, installed on a FLARE VM (Windows 10 Pro): installed fine, but the scan errored immediately with `Method invocation failed because [System.Security.Cryptography.SHA256] does not contain a method named 'HashData'.`

- [x] **REAL BUG FOUND AND FIXED: `::HashData()`/`[Convert]::ToHexString()` are .NET 5+-only APIs - PowerShell 7.0 (still on .NET Core 3.1) doesn't have either, and a `winget install`-provisioned FLARE VM landed on 7.0 while the host machine already had a newer PowerShell 7.x.** PowerShell 7 is self-contained (bundles its own .NET runtime per release: 7.0→.NET Core 3.1, 7.1→.NET 5, 7.2→.NET 6, and so on) - which exact .NET version a machine gets depends entirely on which PowerShell 7.x release actually got installed, not the underlying Windows version. `SHA1.HashData()`/`SHA256.HashData()` (one-shot static hash shortcuts) and `Convert.ToHexString()` (byte-array-to-hex-string) were both introduced in .NET 5.0 - code using either silently requires PowerShell 7.1+, a constraint that was never stated anywhere (README says "PowerShell 7+") and never hit in this dev sandbox (no `pwsh` here to test with at all) or on the host machine (already had a newer PowerShell 7.x from some earlier point). Found **8 total call sites** across the file, not just the one in the error message - the main per-file SHA-1/MD5 hash loop (every file, every scan) uses `[Convert]::ToHexString()` twice; `Get-ArchiveDestDir` (archive expansion) and two duplicated NSRL-cache-path-hash blocks (the real scan's pre-scan setup, and the Settings page's "reload NSRL cache" preview button) each use one `::HashData()` + one `ToHexString()` pair - fixing only the one in the error message would have hit the identical error again on the very first file hashed, the same "fix bug #1, immediately hit bug #2" pattern this project has hit before with FLARE VM testing, so all 8 were fixed together in one pass rather than one at a time. **Fixed** by replacing every `::HashData(bytes)` with the older, universally-compatible `::Create()` + `.ComputeHash(bytes)` instance pattern (existed since .NET Framework 1.1), and every `[Convert]::ToHexString(bytes)` with `[System.BitConverter]::ToString(bytes).Replace('-', '')` (same uppercase-hex output, no casing change downstream) - both existed on every .NET version PowerShell 7 has ever shipped, not just the newest ones. Bracket/brace/paren balance re-verified on just the diff's added/removed lines via the same quote/comment-aware scanner used for every other Rowan-only change this dev sandbox can't run `pwsh` to check directly (net delta: 0 across all three bracket types). **Not yet re-tested against a real scan on the FLARE VM** - needs a fresh installer build and a real re-run there to confirm the scan now completes.

## Second real Winnow installer test - 2026-08-13

Fresh installers built via the "Run workflow" manual trigger (see the Actions page - a plain commit push doesn't build anything, only a tag push or a manual dispatch does) and installed on the host system.

- [x] **REAL BUG FOUND AND FIXED: Winnow crashed at startup with an unhandled `PermissionError: [WinError 5] Access is denied: 'C:\\Program Files\\BinSifter Winnow\\Reports'`.** Traceback: `__main__.py` -> `main_window.py:__init__` -> `config.py:build_default_config()` -> `pathlib.py:mkdir`. Root cause: `Winnow.iss` deliberately offers a choice between a per-user install (default, lands under `%LOCALAPPDATA%\Programs`, always writable) and an all-users/admin install (lands under `C:\Program Files`, requires elevation to write to) - this install went down the admin path, and `build_default_config()`/`save_settings_cache()` both unconditionally assumed the install directory (`get_binsifter_root()`) was writable, trying to `mkdir` Reports/Attack/Blocklist and write the settings-cache JSON directly under it on every startup with no fallback. A non-elevated launch (which is how GUI apps normally run, even after an elevated install) can never write to Program Files, so this crashed on literally every launch of an admin-mode install, not just occasionally. **Fixed** by adding `get_binsifter_data_root()` in `config.py`: it still starts from `get_binsifter_root()`, but actually probes for real write access (creates and deletes a small probe file, rather than trusting permission bits, which don't reliably predict actual NTFS/UAC write access) and falls back to `%LOCALAPPDATA%\BinSifter Winnow\` - always writable, no elevation needed - if that probe fails. `build_default_config()` and `save_settings_cache()` now both go through this instead of `get_binsifter_root()` directly; `get_binsifter_root()` itself is untouched and still used as-is for the read-only logo-loading paths in `main_window.py`/`about.py`, which don't need write access and shouldn't change behavior. Working through it: archive expansion doesn't need to happen inside the per-file worker pool at all, in either variant. It runs as a **serial pre-scan step**, in the exact same place NSRL/blocklist/YARA/capa already get loaded once, before the pool/runspace-pool is created. **Winnow**: that pre-scan step already runs on a background **QThread** (`main_window.py`'s `_ScanWorker`), in the *same process* as the GUI, not a separate `multiprocessing.Pool` process - a QThread can signal the GUI thread and block on a `threading.Event` for an answer using ordinary, safe Qt cross-thread coordination. **Rowan**: the dispatcher runs in its own PowerShell *runspace* (a thread, not a process, sharing the same in-process memory as the GUI runspace) - rather than a direct cross-runspace `Control.Invoke()` (untested and genuinely risky to get right blind, with no Windows/WinForms environment available to verify it in), this reuses the SAME polled-shared-state pattern the dispatcher already relies on for pause/stop/progress: `$ScanControl` (a `[hashtable]::Synchronized(...)`) grows 3 new fields (`PendingPasswordRequest`/`PasswordMap`/`PasswordMapReady`), the dispatcher sets the request and polls-and-blocks on `PasswordMapReady`, and `$refreshTimer.Add_Tick` (the same 750ms UI-thread timer that already drains logs/dirty-record queues) notices the pending request, shows `Show-ArchivePasswordDialog`, and writes the answer back. Same "block a background worker, let the UI thread answer" shape as Winnow, built out of each variant's own already-proven cross-thread/cross-runspace primitives rather than either forcing one variant's mechanism onto the other or inventing a third, unverified one. By the time either variant's worker pool actually starts, every extracted file is just an ordinary file on disk with a real path - the pool/runspace-pool workers themselves needed **zero changes** in either variant.

  Two sub-questions that weren't put directly to a decision (format scope / password-prompt architecture / Results display were judged the three load-bearing ones) got documented defaults instead of blocking on an answer, same in both variants:

Easy to change later, not worth blocking on.

## AI-assisted triage exploration (local LLM, prototype only)

- [x] **CONCLUDED 2026-08-08 - not viable on real hardware, parked (not deleted).** `prototype_ollama_triage.py` (repo root), deliberately never wired into engine.py/either GUI. Before starting work on Ingot, the idea came up to explore whether a locally-running model (via Ollama) could read BinSifter's already-extracted findings for a suspicious file (YARA hits, capa detections, ssdeep/imphash clustering, Authenticode status, extracted IOCs, ATT&CK mappings) and produce a useful hypothesis about likely intent - fully offline, since case data (live malware samples and their findings) shouldn't leave the analyst's machine.

Root cause isolated by comparing `ollama serve`'s verbose startup log across attempts: `OLLAMA_NUM_GPU=0` did NOT prevent GPU offload in this Ollama version (still showed `offloaded 29/29 layers to GPU`); setting `CUDA_VISIBLE_DEVICES=-1` DID work, but not by forcing CPU-only as expected - it hid the CUDA device specifically, and Ollama fell back to its **Vulkan** compute backend on the same physical GPU instead, which loaded and generated successfully (confirmed via full `resolve_fused_ops`/timing output in the log, ~20 tokens/sec, real completion) with flash attention still enabled and all layers still offloaded - so the crash is specific to Ollama's bundled CUDA runtime on this Pascal-generation card, not to GPU acceleration, flash attention, or model choice in general. **Fix: `[Environment]::SetEnvironmentVariable('CUDA_VISIBLE_DEVICES', '-1', 'User')` set as a persistent user env var** (not just in one PowerShell session), so Ollama's normal background/tray app picks it up too, not only a manually-run `ollama serve`. ## AI export (Markdown + JSON, both variants) - 2026-08-08

The safer follow-up to the AI-assisted triage exploration above: instead of running any AI *inside* BinSifter (the approach that led to the GPU/display lockup), BinSifter now formats one file's already-extracted findings into a compact Markdown document and a matching JSON object, for the analyst to hand to whatever AI they want - paste the Markdown into a cloud chat interface, or feed the JSON to a script hitting a local model's own API. BinSifter itself never runs or calls out to any AI here, cloud or local - this is pure data formatting, with none of the inference risk, network calls, or new attack surface the prototype above had. Implemented in both variants in the same pass, per the standing convention.

- [x] **Winnow: `binsifter/core/ai_export.py` (new module).** `compact_record()` strips a `FileRecord` down to only the fields worth an AI's attention - empty string/0/`False`/-1 (BinSifter's generic "not computed" sentinels) are dropped, plus one field-specific sentinel (`YaraSeverity`'s `"Unknown"` default, which means the same "nothing to assess" thing `YaraSeverityScore`'s -1 does, just spelled as a word). `Path`/`MD5`/`SHA1` are always kept as the file's identity even if empty; `Disposition` is always kept even at its `"Untriaged"` default, since that's a real triage state rather than a "not computed" placeholder. ## Multi-vendor antivirus detection (both variants) - 2026-08-08

Raised directly: the Defender exclusion button only ever helps if Windows Defender is the machine's active antivirus product - on a machine running a different AV, that button does nothing useful and gives no indication why. This adds detection of whatever's actually registered, plus guidance for where to add the exclusion manually when it isn't Defender. Scope chosen deliberately narrow (detect + guide, not automate every vendor): most non-Defender products either have no stable local CLI for scripting an exclusion at all, or - for the enterprise EDR products especially (CrowdStrike, SentinelOne, Symantec/Broadcom managed via SEP Manager) - intentionally block local self-exclusion by design, since letting a local process silently exempt itself from EDR scanning is exactly the kind of thing EDR exists to prevent. Automating a scripted exclusion for those would be building something that either can't work or shouldn't.

- [x] **Winnow: `binsifter/core/av_detect.py` (new module).** Reads `root/SecurityCenter2`'s `AntiVirusProduct` WMI class - the same class Windows' own Security app reads, not a BinSifter invention - via a non-elevated `powershell.exe -Command "Get-CimInstance ... | ConvertTo-Json"` subprocess call, same shell-out pattern `defender.py` already uses (no `wmi`/`pywin32` dependency added). Unlike the actual Defender exclusion, reading this class needs no Administrator rights on any supported Windows version. `detect_av_products()` returns deduplicated `AvProduct` names; an empty list is a normal, valid outcome (Windows Server - the underlying Security Center service is client-SKU-only - Security Center disabled, or genuinely nothing registered), not an error - `AvDetectionError` is reserved for hard failures (non-Windows, `powershell.exe` missing, timeout). `guidance_for()` looks up a short, honest pointer to where ~17 common vendors' own exclusion settings live (McAfee, ESET, Sophos, Symantec/Broadcom, CrowdStrike, SentinelOne, Bitdefender, Kaspersky, Trend Micro, Malwarebytes, Avast/AVG, Webroot, F-Secure, Norton, plus both Defender name variants pointing back at the automated button), falling back to a generic "check its settings" message for anything unmatched. ## Rowan startup: $BinSifterRoot defaulting to C:\Windows\System32

- [x] **Fixed 2026-08-08.** Hit while testing the archive feature: launched Rowan and got two stacked warning dialogs - "couldn't determine its own script folder... will be created under the current folder instead: `C:\Windows\System32`", immediately followed by "default folder isn't writable... will be created here instead: `C:\Users\Jay\AppData\Local\BinSifter`". The second dialog's fallback (a per-user, guaranteed-writable folder) already made this harmless in practice, but it was correctly flagged that System32 should never have been the *candidate* default in the first place - "The default should be the GitHub directory or whichever directory Rowan is launched from."
  - **Root cause:** `$PSScriptRoot`/`$PSCommandPath`/`$MyInvocation.MyCommand.Path` all came back empty for this launch (same class of gap the code already called out - certain VS Code "Run and Debug" configs, or any invocation that doesn't leave a real, plain `.ps1`-file-backed script context, don't populate these the normal way). The old fallback for that case was `(Get-Location).Path` - PowerShell's own session *current directory*, which is a completely different thing from "where the script file lives" or "where Rowan was launched from," and for several real launch paths (a shortcut with no "Start in" set, some debug configs) that current directory defaults to `C:\Windows\System32` since that's where `powershell.exe` itself lives - not because BinSifter's own folder is anywhere near there.
  - **Fix:** added a fourth resolution tier, tried *before* giving up and guessing: parse this process's own command line (`Get-CimInstance Win32_Process -Filter "ProcessId=$PID"`) for a real `.ps1` path. This works regardless of which automatic variable failed, since the actual script path is always present as a literal command-line argument no matter how PowerShell was invoked (double-click, right-click "Run with PowerShell", a shortcut, VS Code Run/Debug, `pwsh -File`, `-Command "& '...'"`) - genuinely finds "whichever directory Rowan is launched from" as originally requested, rather than guessing. Only if that also comes up empty (e.g. the script's text was piped/typed into a session with no real file backing it at all) does it fall through to a last resort - and that last resort is now `%LOCALAPPDATA%\BinSifter` directly, not `Get-Location`, so System32 (or any other surprising session-CWD artifact) can never again show up as a candidate root, not even transiently in a dialog. The existing writability belt-and-suspenders check (added 2026-08-03 for this exact System32 case, previously the only defense) stays in place unchanged as a second layer, for the separate scenario of a *correctly*-resolved script folder that happens to live somewhere the current user can't write to (a read-only mount, a locked-down machine, etc.).
  - **Verification caveat, same as the rest of Rowan's port this cycle:** no interactive Windows/WinForms environment in this dev sandbox to actually run this and confirm the CIM-based lookup resolves correctly end-to-end - verified via careful manual read-through and the mechanical brace/bracket/paren balance check (balanced: 1185/1185 braces, 1047/1047 brackets, parens at the same pre-existing -1 baseline as before this edit). Worth relaunching however this was originally triggered (sounds like it wasn't a plain double-click or `pwsh -File`, since those already worked correctly before this fix) to confirm it now resolves to the real BinSifter/GitHub folder instead of prompting at all.

## Catalog-based (.cat) signature verification

- [x] **Implemented in Winnow 2026-08-08 - Rowan needed zero code changes.** Added directly after the "38 unparseable files" investigation surfaced the separate, longer-standing gap noted in `authenticode.py`: a large fraction of Windows' own inbox binaries (notepad.exe, calc.exe, etc.) aren't embedded-signed at all - they're validated against a system catalog file (`.cat`, under `C:\Windows\System32\CatRoot\`) instead, and `check_signature()` was previously only checking each file's own embedded PE certificate table.
  - **Rowan: confirmed to need no changes at all.** Rowan calls the native `Get-AuthenticodeSignature` cmdlet, which goes through Windows' own `WinVerifyTrust` under the hood - and `WinVerifyTrust` already checks catalog files transparently as part of normal signature verification on any real Windows machine with an intact `CatRoot`. This gap only ever existed in Winnow, which does its own PKCS#7/trust-chain verification via `signify` instead of deferring to the OS. Per the "implement across all variants" convention (see Conventions section at top), this is the one legitimate exception: there's nothing to port because Rowan was never missing the behavior in the first place.
  - **Winnow implementation:**
    - `core/config.py`: new `CatalogDirectory` Settings-page field (default `""`), added to `_CACHE_FIELDS`. Optional, same as `GhidraDir` - blank means "skip catalog checks," not an error.
    - `core/authenticode.py`: new `parse_catalogs(catalog_directory)` - enumerates every `*.cat` file directly under the directory and parses each into a `CertificateTrustList` via `CertificateTrustList.from_envelope()`; a single malformed `.cat` is logged and skipped, not fatal to the batch. `check_signature()` gained an optional `catalogs` parameter - each provided catalog is offered to the file via `AuthenticodeFile.add_catalog(catalog, check=True)` before `explain_verify()` runs; `check=True` means signify itself only actually attaches a catalog if the file's hash is found inside it (`find_subject()`), so passing every configured catalog to every file is safe and cheap. `iter_signatures()`'s existing default `signature_types="all"` already combines embedded + catalog signatures, so no other verification-path changes were needed.
    - `core/engine.py`: catalogs are parsed **once per worker process**, not once per file - `_pool_worker_init()` calls `authenticode.parse_catalogs(config.CatalogDirectory)` at worker startup and stores the result in a new `_worker_catalogs` global, mirroring the existing YARA-rules-compiled-once-per-worker pattern (a parsed `CertificateTrustList` wraps `cryptography` objects that aren't cleanly picklable across the `multiprocessing.Pool` process boundary, the same reason YARA's compiled `Rules` object is re-compiled per worker rather than handed down from the parent). The per-file worker call is now `authenticode.check_signature(path, catalogs=_worker_catalogs)`.
    - `gui/pages/settings.py` / `gui/settings_validation.py`: new "Catalog (.cat) directory - optional" Settings field, folder picker, validated the same way as `GhidraDir` (blank is valid; if given, must be a real existing directory) - factored into a shared `_OPTIONAL_DIR_FIELDS` loop rather than a second hand-copied `GhidraDir`-shaped `if`/`elif` block.
  - **Tests:** `tests/test_authenticode.py` gained coverage for `parse_catalogs()` (blank/missing/empty/non-`.cat`/malformed-`.cat`/file-instead-of-directory inputs, all degrading gracefully to an empty list rather than raising) and `check_signature()`'s new `catalogs` wiring (every provided catalog gets offered to `add_catalog()`; one catalog raising doesn't sink the others or the overall check; omitting the parameter entirely is unchanged from pre-2026-08-08 behavior) using a lightweight fake `AuthenticodeFile` stand-in rather than real crypto. Full suite: 173 tests, 170 passed - same 3 pre-existing/unrelated failures as before this work (confirmed via `git show HEAD:...` comparison: 2 in `test_engine.py` around capa-rules-corpus/progress-status gaps in the dev sandbox, 1 in `test_capa_scan.py` - none touch authenticode/catalog code, none introduced by this change).
  - **What's NOT done yet - a real `.cat` file was never obtained, so this is unit-tested plumbing, not end-to-end-verified against a genuine catalog.** The original ask (2026-08-07) was to "pull a known good cat and place it temporarily in the project directory" for testing. That could not be completed from this dev sandbox: there's no Windows machine here to pull one from directly, and the most likely alternative source - `signify`'s own library test fixtures (`oem89.cat`, `catfiletest.cat`, etc., referenced in its `tests/authenticode/file_types/test_ctl.py`) - turned out to be excluded from the PyPI sdist entirely (`tests/test_data/` isn't packaged), and fetching them from GitHub directly was blocked at every turn: `raw.githubusercontent.com`, `api.github.com`, and `codeload.github.com` all return `403 blocked-by-allowlist` from this sandbox's network policy (only the plain `github.com` web UI is reachable, which redirects tarball downloads straight into the blocked `codeload.github.com`). **What's ready to go:** a `Catalogs/` folder now exists at the repo root, gitignored (see `.gitignore` and `Catalogs/README.txt`) exactly as asked - drop a real `.cat` there (e.g. copied from a real machine's `C:\Windows\System32\CatRoot\{GUID}\`, which counts as "known good" since that Windows install already trusts it) and point Settings' new "Catalog Directory" field at it to exercise this for real.
