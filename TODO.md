- [x] **ssdeep per-file cost investigated (2026-08-06).** Root cause confirmed via direct source read + benchmark, not a BinSifter bug: `ppdeep`'s `_spamsum()` core is a pure-Python per-byte loop, no C acceleration, measured at ~850-890ms/MB (~1.16 MB/s) directly. That's inherent to the library, not fixable without swapping it out. Applied the one safe, no-tradeoff win: `compute_ssdeep_hash()` now uses `ppdeep.hash_from_file(path)` instead of `open()+read()+ppdeep.hash(data)`, avoiding one full redundant in-memory buffer copy (`ppdeep.hash()` re-wraps bytes in a `BytesIO` and re-reads it in 64KB chunks regardless of how it got the data). Real savings on large files, not a rounding error, but doesn't change the fundamental ~1.16 MB/s ceiling - swapping `ppdeep` for a C-accelerated ssdeep binding would be the only way to meaningfully move this number, and isn't attempted here.
- [x] **Authenticode trust store corrected (2026-08-05/06).** The "BinSifter doesn't populate a real root CA trust store, expect NotTrusted not Valid" claim baked into `authenticode.py`'s docstring/TODO was wrong - never actually verified, just assumed. ## Quick-launch context menu (Results grid right-click)

Three issues Steve found doing a real right-click pass over the menu, 2026-08-06.

- [x] **Speakeasy/Sigcheck quick-launch could hang the whole app - real thread-safety bug, fixed (2 rounds).** `results.py`'s `_start_captured_tool()` connected `worker.finished`/`worker.failed` to plain lambdas with no explicit connection type. PySide6 only auto-detects a cross-thread connection by inspecting the *receiver*'s QObject thread affinity through the bound method a signal is connected to - a lambda isn't a QObject-bound slot, so that detection can't see through it, and PySide6 silently falls back to a DirectConnection: everything the lambda calls (`_teardown_tool_thread()`'s `thread.wait()`, and `_show_tool_report()`'s `QDialog`/`QMessageBox` construction) ran on the background worker thread instead of the main thread. That's a thread calling `.wait()` on itself (self-deadlock) plus cross-thread widget parenting - exactly matches what Steve hit: `QThread::wait: Thread tried to wait on itself` and `QObject::setParent: Cannot set parent, new parent is in a different thread`, app then unresponsive short of Task Manager. **Round 1 fix** (explicit `type=Qt.ConnectionType.QueuedConnection` on the same lambda `.connect()` calls) did not hold - Steve hit the identical crash again running Sigcheck (same shared method), plus new `QBasicTimer::stop` spam. A lambda still isn't a QObject Qt can resolve a receiver-thread from, connection-type override or not. **Round 2 fix**: stopped connecting to lambdas at all - `worker.finished`/`worker.failed` now connect directly to genuine bound methods of `self` (`_on_captured_tool_finished`/`_on_captured_tool_failed`), the one connection shape PySide6's auto-detection is actually documented to handle correctly. `self.sender()` identifies which worker fired (one shared slot now serves every concurrent run), and a plain `worker.title` attribute (set before `moveToThread`/`thread.start()`, so no cross-thread write) replaces what the lambda closure used to carry. This affected **both** Sigcheck and Speakeasy (same shared code path). Winnow-only - Rowan's WinForms events don't have this footgun. No automated test (GUI/Qt code isn't unit-tested in this project - no display in the dev sandbox). **Confirmed working end-to-end (2026-08-06)** - Steve ran Sigcheck (clean report), Ghidra headless (legible confirmation), and Speakeasy (legible warning dialog, emulation completed, results reported) all in one pass with no hangs, no crashes, no terminal spam. Round 2 held.
- [x] **Ghidra headless gave zero feedback on success - fixed in both variants.** Confirmed via Rowan's source that this wasn't a Winnow-only regression - Rowan's `Start-Process` is equally silent on success, only showing a MessageBox on the error paths (missing Ghidra config, missing Report Directory, launch exception). Steve's complaint ("no other windows open, no messages... appears nothing happens") is valid either way. Added a one-time, non-blocking confirmation dialog after a successful launch in both `results.py`'s `_launch_ghidra()` and the PS1's `$ghidraItem.Add_Click` handler, telling the user analysis started and where results will land (`<ReportDirectory>\ghidra_projects\<project_name>`). Headless analysis still runs unattended after that with no progress indicator by design (unchanged) - this is just a "yes, it started" acknowledgment.
- [x] **Sigcheck grayed out - investigated, not a bug.** Asked Steve to check his Tools folder before guessing at a fix (the obvious hypothesis - Sysinternals ships Sigcheck as two separate files, `sigcheck.exe`/`sigcheck64.exe`, and BinSifter's `TOOL_FILE_NAMES` only searches for the literal 32-bit name - would have been a real gap). Steve has since copied both into the Tools folder - should resolve on the next scan/Settings re-save with no code change needed. Worth revisiting the bitness-fallback idea (search for `sigcheck64.exe` too, preferring it) as a small defensive improvement if this ever comes up again for real, but not implemented since there's no confirmed case that needs it yet.
- [x] **`QMessageBox` text illegible (near-black on near-black) - separate bug from the Speakeasy thread issue, fixed.** Steve sent screenshots of the Ghidra success dialog (the new one just added above) and the Speakeasy confirmation dialog, both with the body text almost unreadable against the background. Confirmed this is unrelated to the threading fix above: the Ghidra dialog is a plain synchronous `QMessageBox.information()` call with zero threading involved, yet shows the identical symptom. Root cause: `binsifter/gui/__main__.py` never applies any app-wide `QApplication.setStyleSheet()`/`setPalette()` (confirmed via grep - genuinely nothing exists) - every other widget in the app gets its colors from its own explicit per-widget stylesheet, but `QMessageBox.information/warning/critical()` calls (used everywhere - `main_window.py`, `results.py`, `settings.py`) get zero BinSifter theming and fall through entirely to Qt's own rendering. On a Windows 11 machine with OS-level dark mode on, Qt6 auto-detects that and applies a dark palette to native dialogs, but the auto-derivation has a well-known gap where the background darkens correctly while text-color roles don't lighten to match - not a BinSifter bug in the usual sense, but a real, user-visible defect either way. Fixed with one app-wide stylesheet in `__main__.py` (`_apply_message_box_stylesheet()`) targeting `QMessageBox`/`QMessageBox QLabel` with the same theme colors used everywhere else - covers every current and future `QMessageBox` call site in one place, immune to the OS auto-detection quirk. Winnow-only; Rowan's WinForms `MessageBox.Show()` uses a completely different native rendering path with no equivalent bug, and Steve hasn't reported this on Rowan. **Confirmed fixed (2026-08-06)** - screenshots of the Ghidra and Speakeasy dialogs both show fully legible text now.

## Planned - next session (2026-08-07)

- [ ] **Archive/compressed-file support (zip/gzip/tar/7z/etc.) - requested 2026-08-06, not started.** Steve wants BinSifter to be able to analyze compressed files, including examining every file inside an archive once decompressed, not just the archive container itself. Three parts to this, in his own words:
  1. Decompress and scan the contents of archive files (zip, gzip, tar, 7z, "etc." - need to pin down the exact format list with Steve before starting; zip/tar/gzip are stdlib-only in Python via `zipfile`/`tarfile`, but 7z needs a third-party library (`py7zr`) and anything RAR-shaped needs another (`rarfile`, which itself needs an external `unrar`/`unar` binary on the system - same "not a pure-Python library" situation `ssdeep`/`sigcheck` are already in).
  2. If an archive is password-protected, prompt the user for a password to unlock it.
  3. If the password isn't known/provided, save that archive into a new, separate directory so the user can run it through dedicated cracking tools (John/hashcat/etc.) outside BinSifter.

  Real open design questions to resolve before/while implementing, flagged rather than silently decided (same "ask before assuming" pattern as everywhere else in this codebase):
  - **Password prompting during a multiprocessing scan is an architecture problem, not just a UI one.** `engine.py`'s scan pipeline runs file processing across a `multiprocessing.Pool` of separate worker *processes*, not just threads - there's no existing mechanism for a worker process to pop a Qt dialog on the main GUI thread and block waiting for an answer (the GUI itself lives in the main process). Options: (a) a pre-pass that identifies all password-protected archives in the source directory before the real scan starts, prompts for all of them up front (one dialog, or a batch list), then feeds passwords into the worker pool via the existing initargs mechanism (same pattern nsrl.py/yara rules already use to hand data to workers); (b) skip protected archives during the parallel pass entirely and handle them serially on the main thread in a second pass after the pool finishes; (c) something else. Needs a real decision, not a guess baked into the first draft.
  - **Nested archives (a zip inside a zip, etc.)** - scan recursively, and if so to what depth (or is one level enough for realistic casework)?
  - **How do extracted files show up in Results?** As their own rows with a "source archive" column/field pointing back at the parent, or grouped/nested under the archive's row somehow? Affects `FileRecord`, the CSV schema, and the Results grid.
  - **Where do extracted files live on disk during/after a scan** - a temp directory cleaned up after, or kept under Reports for later reference? Matters for disk space on a large archive and for whether Ghidra/Sigcheck/Speakeasy quick-launch (which need a real file path) can be pointed at something extracted from an archive.
  - **The "save unprotected-by-us archives for external cracking" directory** - a fixed location next to Reports (matching how `ghidra_projects`/`generated_rules` already work), presumably. Worth confirming the name/location with Steve rather than guessing.

  Given the multiprocessing/password-prompting question in particular, this is worth a real design pass (maybe even a short back-and-forth with Steve on the open questions above) before writing code, not a "just start coding and see" feature - flagging that now rather than at the start of tomorrow's session.
